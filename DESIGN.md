# Design

## Source of truth
- Status: Active

- Evidence reviewed: `ios/InjectionMVP`, `ios/DDLaminateMVP`, `android/InjectionMVP`, `android/DDLaminateMVP`, `src/frontend/imperialax`, `src/frontend/dd-laminate`, `src/frontend/simple-injection`, design files and ImperialAX brand assets, the live Laminate/Injection root and `/v2` web surfaces, the 2026-08-14 desktop Laminate empty/result screenshot supplied during review, `docs/imperialax-forecast-ui-redesign.md`, `docs/imperialax-forecast-ui-rebuild-concept.md`, `docs/OPENRADIOSS_LAMINATE_CONVERSION.md`, the Laminate response API and current SVG ply-stack renderer, the generic visualization API schemas/stubs, the Injection Three.js/GLTF viewer assets, and official product references from Palantir AIP/Workshop, Monolith, Ansys SimAI, Neural Concept, Altair PhysicsAI, Hebbia Matrix, LangSmith, Glean, and Dust.

## Brand
- Personality: technical, precise, calm, high-trust engineering software.
- Trust signals: clear model/readiness status, legible charts, restrained colors, numeric hierarchy.
- Avoid: generic marketing hero layouts, decorative blobs, overly playful visuals, gratuitous accent colors, and low-contrast gray-on-gray controls.

## Product goals
- Goals: make prediction inputs fast to scan, make results and chart markers immediately interpretable, keep app names simple, and explore a Wanted UI Kit-inspired v2 without losing the existing production-like screens.
- Non-goals: forced full design-system rewrite, destructive replacement of existing screens, decorative illustration work, or broad backend/API changes for a visual experiment.
- Success signals: users recognize Laminate and Injection as one product family, can distinguish them through engineering content rather than arbitrary UI differences, read the top result without hunting, and switch between established and v2 screens during review.

## Personas and jobs
- Primary personas: CAE/AI researchers, engineers, and internal testers.
- User jobs: check API readiness, select model/input set, run a forecast, inspect result curve and critical metrics.
- Key contexts of use: phone-first review, lab/office use, local and public API endpoints.

## Information architecture
- Primary navigation: login-gated unified workspace for ImperialAX; module-specific forecast screens inside each native app. The native unified app entry should mirror `ai.imperialax.com/index.html` for login, account status, workspace summary, and module card hierarchy.
- Core routes/screens: web login, web login Korean, module workspace, module workspace Korean, account/access dialogs, Laminate v2 forecast, Injection v2 forecast, forecast inputs, latest result, full result.
- Content hierarchy: account status, module access, utility access to research purpose and AI Assistant, model/input controls, primary prediction button, and forecast results. Research context and assistant conversation open from the shared top-right utility area instead of permanently pushing the engineering workspace downward. The separately addressable Laminate rebuild concept separates quick screening from deep-dive analysis, swaps result content in place through Summary/Curve/XAI/Design Space tabs, promotes sortable run comparison to a first-class section, and groups the six supported response models into 3-Size Pt-Consistent and production model families.

## Design principles
- Principle 1: results should read before decoration.
- Principle 2: Laminate and Injection established screens use one shared product-family shell. Header geometry, utility controls, typography, spacing, surfaces, forms, buttons, workflow strip, panels, empty states, result hierarchy, XAI grammar, breakpoints, and interaction feedback are identical by role; only engineering inputs, visualizations, terminology, and result content may differ.
- Principle 3: v2 experiments must be reversible and separately addressable from Classic screens.
- Principle 4: the Laminate monotone concept should express hierarchy through black/white surface changes, weight, rules, and spacing before introducing color.
- Principle 5: the lighter logo-background concept preserves the established v2 colors and components; brand expression is limited to low-opacity official marks in non-interactive background areas.
- Principle 6: long result pages must keep the setup panel available for iteration and progressively disclose secondary XAI features and research detail through native accessible accordions.
- Principle 7: the Laminate rebuild concept must keep page height predictable by replacing result content through tabs rather than stacking every analysis section.
- Principle 8: quick screening and deep-dive analysis are explicit, mutually exclusive modes; the mode control uses `radiogroup`/`radio` semantics rather than tab semantics because it changes available tools instead of switching one tabpanel.
- Principle 9: each forecast product has one unmistakable engineering hero. Laminate leads with the response curve, Pt transition, and ply fingerprint; Injection leads with the 3D pressure field and synchronized sprue-pressure curve.
- Principle 10: trust is part of the primary result, not a separate report. Model identity, supported data domain, interpolation/extrapolation state, reliability, and the path to XAI remain visible beside the hero result.
- Principle 11: desktop forecast screens use one document scroll. Internal scrolling is reserved for bounded tables or code-like payloads, never for the main result workspace.
- Principle 12: ply visualization has two levels. Summary uses a compact 2D sequence fingerprint for immediate comparison; the Ply Sequence tab owns the large 3D stack, full 16-ply order, orientation legend, and per-ply inspection. Sequence-map direction lines rotate to the actual ply angle rather than reducing orientation to positive/negative states, and the 3D plate length and width respond independently and immediately to the panel-dimension inputs while preserving a stable, centered inspection viewport.
- Principle 13: result summaries use one descriptive section heading and one uniform metric scale. Type, probability, Pt, force, and displacement share the same card treatment; model/domain/reliability context sits in a compact metadata row, and color is reserved for states that require interpretation.
- Principle 14: the Laminate rebuild reuses the proven v2 analysis interactions instead of simplifying away engineering detail. The Curve tab preserves the raw response, P1 fit, Pt marker, button/wheel zoom, and post-zoom drag; Design Space preserves Type encoding, current-case emphasis, and per-dot hover/tap detail.
- Principle 15: XAI never truncates the model feature set. Keep the five strongest local features immediately visible for scanning, then place every remaining feature from the response in one native, keyboard-accessible disclosure with an explicit remaining-feature count.
- Principle 16: Summary and Curve are two views of one response, not separate interpretations. They must share the exact raw points, domain, P1 fit, Pt intersection, and responsive aspect-ratio family; Summary may remove axis labels and controls, but it preserves the detailed chart's visual encoding.
- Principle 17: Forecast results must begin empty. Never present deterministic preview values as if a model has already run; offer one explicitly labeled example on demand, and keep examples out of run history so executed and illustrative data cannot be confused.
- Principle 18: Injection keeps its DOE-driven 3D shape preview visible before prediction because it explains the current input, not the model output. Its result tabs and deep-analysis guidance remain hidden until an actual or explicitly requested example result exists; validation stays unavailable for examples because no model response exists to compare.
- Principle 19: Laminate and Injection share one XAI reading grammar without becoming visually identical: show the five strongest local Features first, disclose the full remainder, retain aligned contribution bars, and explain every Feature with a localized name, engineering category, physical meaning, current value, local sensitivity, and masking condition. Canonical symbols such as `D11`, `A12`, and `θ₁` remain unchanged across languages.
- Principle 20: Laminate and Injection rebuilds share one desktop shell geometry: the command bar joins directly to a light canvas workspace, Forecast setup and result cards sit 18px inside that workspace, the setup rail is 400px wide, and the inter-panel gap is 18px. They also share header typography, status, current-UI link, and language switcher. Product-specific module shortcuts do not appear in one rebuild header unless they appear in both; product identity comes from the title and engineering content rather than divergent utility navigation.
- Principle 21: Injection controls distinguish trained variables from fixed experiment conditions. Each editable numeric value appears exactly once as one localized label with its unit and one plain bordered field; duplicate value readouts and decorative progress bars are not shown. Gate type and size remain visible as one full-width, neutral read-only condition row below the geometry fields, with separate type and size values plus a small `Fixed` status. It must never collapse into a narrow geometry grid cell, compete with readiness states through green styling, or resemble an editable control. The locked training condition (`edge gate`, `10 × 1.5 mm`) cannot be edited or submitted outside that supported DOE until gate-varied training data exists.
- Principle 22: Laminate and Injection use the same typography and control scale whenever an element has the same role and position. Forecast setup eyebrows, titles, descriptions, field labels and values, primary actions, analysis headings, empty states, and result tabs share the Laminate rebuild sizes, weights, line heights, and control heights; product differences come from engineering content, not arbitrary type scaling.
- Principle 23: The Laminate Curve tab remains an inspection surface on phones, not a shrunken desktop chart. Summary and Curve use the same wide rectangular mobile aspect, compact axis padding and legends, preserve button and one-pointer pan controls, support two-pointer pinch zoom around the gesture midpoint, and reduce the Pt annotation to a compact badge so the marker never dominates the visible plot.
- Principle 24: Laminate deep-analysis tabs remain fully visible as one compact row on phone widths. Panel descriptions use short Korean-first one-line copy, and the Design Space scatter plot receives a near-square mobile inspection viewport instead of inheriting the shallow desktop aspect ratio.
- Principle 25: Laminate and Injection XAI use the same feature-reading grammar: white neutral cards, an inline category chip, supporting description and local-value metadata, a 7px solid-blue contribution bar on a neutral track, and a right-aligned percentage. Product identity may differ around the XAI panel, but not in the meaning or visual scale of feature influence.
- Principle 26: Injection Filling Pressure distribution uses compact comparison rows with one shared visual grammar: aligned group labels, a 7px solid-blue ratio bar on a neutral track, and right-aligned tabular percentages. Avoid per-bar gradients or decorative color changes that imply a second variable not present in the data.
- Principle 27: On desktop, a newly completed Laminate forecast must reveal its complete Summary inside the existing right-hand Analysis workspace without requiring a second scroll. Preserve the five metrics, response curve, Ply fingerprint, and compact trust context, but use a low, wide summary chart and tighter result-only spacing; Curve, Ply Sequence, XAI, and Design Space remain opt-in detail tabs.
- Principle 28: Established Laminate and Injection screens share one repo-owned CSS and interaction layer for their common shell. Product-local styles may extend it only for genuinely module-specific controls or engineering visualizations; they must not redefine shared component roles.
- Principle 29: `Research purpose` and `AI Assistant` are matching header utilities on both established products. Each opens a keyboard-accessible modal window, restores focus to its trigger when closed, closes through an explicit button, Escape, or backdrop click, and never removes the user from the current forecast state.
- Principle 30: Progressive utility windows do not compete with the forecast workspace. Research copy is concise and scannable; Assistant history and citations remain inside the modal with bounded viewport height while the main page retains one document scroll.
- Principle 31: Established Laminate prediction modes are mutually exclusive views. `Response forecast`, `u3`, `Stack Lab`, and `Curve CSV` keep one active form at a time; shared product-family styling may align their visual roles but must never override a module's hidden or active-state contract.
- Principle 32: The official ImperialAX mark-and-wordmark is the first visual element at the top-left of the AI workspace and every module header. It links back to the relevant workspace home, preserves the supplied asset ratio, and sits above—not in place of—the page or module title. Text-only recreations of the wordmark are not used when the official asset is available.
- Principle 33: Established product headers organize utilities by user intent, not implementation order. Module navigation and AI help form the primary action group; research context, locale, account action, and API readiness form the secondary group in that order. Navigation, assistance, information, language, account, and status each keep a distinct but restrained visual role, and the same order is preserved in Laminate and Injection across Korean and English.
- Principle 34: Established Laminate and Injection keep their approved visual shell while splitting long results into accessible in-place tabs. Laminate uses Summary, Curve, XAI, and Design Space; Injection uses Summary, Sprue Curve, Filling Distribution, XAI, Validation, and History. Tabs change only result content and never duplicate model outputs.
- Principle 35: Slow prediction states use an indeterminate in-page progress card in the result workspace. It names the current preparation stage, sets `aria-busy`, and never invents a percentage or completion time that the server cannot guarantee.
- Principle 36: Model disagreement is a review state, not an error and not a confidence vote. Machine Learning is the primary screening result; Deep Learning and Hybrid are sensitivity checks. A Type mismatch near a learned decision boundary requires CAE or experimental confirmation.
- Principle 37: Ply stack labels are inspection aids, not decoration. The 3D stack shows only the first and final ply endpoint markers (`P1` and `P16` for the standard stack); the full order remains available in the sequence map and accessible label.
- Principle 38: Public web routes have one canonical inventory in `docs/IMPERIALAX_WEB_ROUTE_MAP.md`. Root, locale, generation, account, and admin routes must be host-aware and covered by regression tests before deployment; legacy routes redirect to their canonical equivalent instead of serving divergent UI.
- Principle 39: Injection result charts include one compact, localized reading guide inside the chart card. Sprue Curve explains axes, peak meaning, and transition sensitivity; Filling Distribution explains the low-to-high pressure-bin order, volume-ratio bars, and the absence of spatial position. Guidance distinguishes surrogate interpretation from Moldex3D or experimental confirmation without repeating the plotted values.
- Principle 40: Established Laminate and Injection workflow guides use the same four-step grammar: choose model(s), set the module-specific case or DOE, confirm editable dimensions and process details, then review primary outputs and supporting evidence. Every core input visible in the forecast form must be represented once in the guide; the cards use four columns on wide screens, two columns on compact desktop or tablet layouts, and preserve the existing mobile simplification.
- Principle 41: Product eyebrows describe the engineering domain rather than a training-data vendor. The matched pair is `복합재 적층 AI` / `Composite Laminate AI` and `사출 성형 AI` / `Injection Molding AI`; Moldex3D remains named only where the UI explains data provenance, validation, or file comparison.
- Principle 42: Established Laminate and Injection hero descriptions use one uninterrupted line on tablet and desktop widths so the product purpose reads as one statement. Phone layouts may suppress or wrap this supporting copy rather than introduce horizontal overflow.
- Principle 43: Laminate stack previews keep orientation lines clipped to each ply surface. The surrounding preview plane remains visually quiet and must not use long perspective or grid guide lines that extend beside or beyond the stack.
- Principle 44: Phone layouts optimize for touch and early task completion without hiding engineering inputs. Header actions, mode controls, result tabs, and forecast actions use at least 44px touch targets; six-tab Injection results use a fully visible 3-by-2 grid; long Injection setup flows offer a preset forecast action before editable detail fields while retaining the detailed fields and final action below.
- Principle 45: Native iOS and Android result workspaces mirror the established web information architecture instead of stacking every analysis artifact in one long page. Laminate uses Summary, Curve, Ply Sequence, XAI, and Design Space; Injection uses Summary, Sprue Curve, Filling Distribution, XAI, Validation, and History. Tabs replace content in place, keep at least a 44px touch target, and show honest unavailable states rather than fabricated analysis.
- Principle 46: Public demo access is one explicit secondary login action, labeled as a demo workspace rather than a sales request. Web, iOS, and Android always call the dedicated demo-session endpoint with the fixed `demo@imperialax.com` identity; typed credentials never flow into that action. The server owns availability and grants only Laminate and Injection entitlements—admin, optimization, and password-based account login are outside the public demo boundary.
- Principle 47: Laminate uses one large result-side `3D Viewer` with two modes, `Deformation` and `Ply Stack`, instead of adding separate mobile tabs for closely related spatial views. The compact setup preview remains an input explanation; the result viewer owns animation, inspection, and solver-result provenance.
- Principle 48: The viewer must distinguish response-linked illustration from a solver- or field-validated result. A shape driven only by predicted Pt, maximum displacement, and the force–displacement curve is labeled `Response-based visualization` and must not display stress contours or imply node-level accuracy. `CAE result` is reserved for retained mesh coordinates, per-frame displacement vectors, and field values from Abaqus or OpenRadioss.
- Principle 49: Deformation playback and the response curve are one interaction. Play/pause, a load-step scrubber, the curve cursor, and the Pt marker stay synchronized; users can reset the view, select an isometric or top view, toggle the undeformed outline, and change deformation exaggeration without changing the predicted values. Touch orbit/pinch and reduced-motion alternatives are first-class states.
- Principle 50: Real field visualization carries visible provenance. Solver, source case or job, mesh size, field name, unit, frame/load step, and deformation scale remain inspectable beside the viewer. A quantitative color legend appears only when the displayed values come from an actual scalar field; unavailable fields use an honest disabled state rather than generated color.
- Principle 51: The first viewer release reuses the repository-owned Three.js rendering approach already proven by Injection and keeps orbit/pinch controls module-local. No new viewer dependency is introduced until the retained OpenRadioss/Abaqus field format and browser payload budget demonstrate a need that the existing stack cannot meet.
- Principle 52: The response-based Laminate deformation view represents the analyzed 16-ply stack as one bonded body. Individual plies may remain visible through touching colored thickness bands, with P1 on the top surface and P16 on the bottom surface, but they must share one continuous global deformation field and never animate as detached cards. Any exaggerated display thickness is disclosed as a visibility aid rather than physical scale.
- Principle 53: `Pt 이전/이후` is supporting state, not a substitute for the experiment-specific Pt value. The Viewer keeps Predicted Pt visible beside current force and adds its ratio to predicted maximum force so results of different magnitude can be compared. A physical force unit is shown only when the dataset or model manifest declares it unambiguously.
- Principle 54: The bonded Laminate Viewer may reuse the Preview's angle-aware fiber lines as an optional inspection overlay. The overlay starts off, rotates each line to its actual ply angle, uses the established positive-angle green and negative-angle red cues, and subdivides the lines so every segment follows the shared curved deformation surface through the full load range. P1 remains the clearest visible surface; buried ply markings obey depth and must not be drawn through the bonded stack.
- Tradeoffs: keep native controls and current code shape over custom-heavy components; translate UI Kit style into ImperialAX workflows instead of copying demo assets literally.

## Visual language
- Color: Injection uses steel/blue with molten orange-red accents; Laminate Classic uses graphite/teal with red Pt accents; Laminate v2 uses a Wanted-inspired white canvas, black command surfaces, blue action accents, light grid texture, and green readiness states. The separately addressable Laminate monotone concept uses near-black `#050505`, white, warm gray work surfaces, and thin neutral rules; red remains available only for errors and destructive warnings. The Laminate rebuild concept uses flat white/light-gray surfaces, 0.5px neutral hairlines, no gradients, and no dark command bar; saturated fill is reserved for the single primary forecast action.
- Typography: native rounded/bold headings and monospaced digits remain available outside the rebuild. The Laminate rebuild concept uses the system sans-serif stack (`-apple-system`, `Segoe UI`, Inter, sans-serif), only 400 and 500 weights, sentence-case English labels, h1 22px, h2 18px, h3 16px, and a maximum 32px result hero label.
- Spacing/layout rhythm: compact cards with 8px radius and dense engineering information; v2 uses compact workflow rows, deliberate wrapping for long headings, no-wrap only for short labels/chips, and two-panel input/result hierarchy.
- Shape/radius/elevation: subtle cards, restrained borders, no nested card structures; v2 keeps 8px radius, thin borders, and soft shadows. The monotone concept removes decorative elevation, uses square or 2px control corners, and reserves circular geometry for compact numbers/status dots. The rebuild concept standardizes cards at 12px radius, controls at 8px radius, 16–20px card padding, 0.5px borders, and no box shadows.
- Motion: keep ambient movement restrained; Injection v2 may use
  user-triggered predicted filling-pressure/fill-front animation after a
  forecast completes.
- Imagery/iconography: SF Symbols/native icons where available; charts remain the main visual asset. The monotone web concept uses the official ImperialAX horizontal logo for identity and the official mark as a large, low-opacity structural watermark, following the approved PPT template.
- Background branding: when applying the ImperialAX mark to the existing Laminate v2 direction, keep it below 5% opacity, clip it inside the header or page canvas, and never place it behind form labels, chart data, or primary actions. Embedded engineering renders inside the Laminate rebuild should use the same light-neutral canvas and hairline grid as the surrounding workspace; retain model-specific colors on the rendered object instead of isolating it on a dark presentation panel.

## Accessibility
- Target standard: high contrast enough for phone use; preserve native text controls.
- Keyboard/focus behavior: native `<details>/<summary>` controls provide keyboard disclosure behavior; shared utility dialogs use native dialog semantics, trap focus while open, close with Escape, and restore focus to the invoking header button. After a mobile forecast completes, the core result summary may receive scroll focus without trapping keyboard focus. Rebuild result tabs support Left/Right, Home, and End keys with synchronized `aria-selected`; the quick/deep `radiogroup` supports the same navigation with synchronized `aria-checked` and roving tabindex. Curve zoom is available through focusable buttons as well as the pointer wheel, Design Space filters use toggle-button semantics with `aria-pressed`, and additional XAI features remain keyboard accessible through native disclosure controls.
- Contrast/readability: avoid light text on saturated backgrounds except white on primary buttons.
- Screen-reader semantics: unchanged in this pass.
- Reduced motion and sensory considerations: keep prediction pressure-map
  motion tied to the forecast result state and avoid extra decorative loops. The Laminate ply preview updates only in direct response to Case or theta input and does not autoplay. Laminate deformation playback starts paused when reduced motion is requested, keeps the scrubber fully usable, and never relies on motion alone to communicate Pt or the active load step.

## Responsive behavior
- Supported breakpoints/devices: iPhone, Android phones, SwiftUI preview/macOS build targets.
- Layout adaptations: mobile web must not be a stacked desktop canvas; use compact
  phone-first headers, short process chips, and vertical module list cards with
  touch-sized actions. The DD Laminate v2 mobile input state should keep the
  active forecast form and primary prediction action inside one phone viewport;
  suppress secondary workflow/setup headers on mobile and use that space for a
  large angle-aware ply stack visual between model selection and theta controls.
  The ply visual should adapt to available mobile height: show the full stack
  aspect on tall/large phones and clamp down on short phones so the primary
  action remains reachable in the first viewport. Injection v2 may scroll on mobile because DOE
  geometry/process inputs are denser, but must hide secondary workflow summaries
  on phone widths, keep compact process controls and the primary prediction
  action visible in the first mobile viewport, and avoid horizontal overflow.
  Injection v2 should disable sticky setup panels on narrow or short windows so
  result review remains the primary scroll focus after prediction. On phones,
  Injection model selectors use the full content width, the v2 process and
  geometry fields retain a compact two-column grid, and the Sprue chart uses a
  landscape viewport rather than a tall portrait viewport. The established
  Laminate Design Space uses a taller inspection viewport on phones instead of
  inheriting its shallow desktop aspect ratio.
- Touch/hover differences: phone-first. Design Space point detail must be available through pointer hover on desktop and pointer/tap selection on touch devices; Case filters provide a non-hover way to reduce overlapping points.
- Long-result behavior: the workflow-redesign setup remains sticky only above 1024px. The rebuild concept defines 1024px and above as desktop with two columns and sticky setup; its Laminate Summary is height-budgeted to the right-hand Analysis workspace so the first result does not add a required scroll. Below 1024px it returns to normal flow, result tabs become horizontally scrollable pills, and the comparison table becomes a card list.

## Interaction states
- Loading: both established products show an indeterminate result-workspace progress card with staged, localized copy while inference runs; a hidden Injection pressure canvas is redrawn after its result tab becomes visible. Loading states expose `aria-busy`, preserve reduced-motion preferences, and do not show fake percentages.
- Empty: Laminate and Injection rebuilds start with result tabs and values hidden, explain that no forecast has run, and offer an optional `예시 결과 보기` action. Examples are labeled `예시 데이터`, state that they are not model-run results, and do not enter run history. Injection retains its DOE-driven 3D input preview and may show device-persisted prior runs separately from the current empty result.
- Error: red status and existing alerts/messages. The rebuild page places forecast errors inline at the bottom of the input panel and never leaves a global warning visible beside a valid result.
- Success: green API status; the rebuild page returns to Summary and appends the run to the comparison table.
- Disabled: existing disabled predict button; loading preserves the button label and exposes the reason through nearby status copy.
- Offline/slow network, if applicable: the rebuild keeps the full six-model selector and deterministic concept results available, labels the header as `시안 데이터 모드`, and replaces concept data with live prediction, local XAI, and design-space responses when the API is reachable.
- 3D preview manipulation: Injection v2 Parametric Preview should match v1's
  free 360-degree drag rotation, plus wheel/button zoom and reset.
- Charts: Injection v2 Sprue Pressure should stay visually close to v1 with
  explicit x/y ticks, grid lines, axis labels, and a readable gradient pressure
  curve.
- DOE editing: Injection v2 should match v1 by switching Geometry or Process
  DOE selectors to `User input` when users manually edit the corresponding
  geometry/process fields.
- Injection input visibility: `공정 세부값`/`Process details` and `형상 세부값`/`Geometry details` are core forecast inputs, so both sections remain visible in Quick screening and Deep dive. Analysis mode may simplify result tabs, but must not hide editable prediction inputs.
- Injection setup ordering: the DOE selector row follows the same process-first reading order as the editable detail cards: `Process DOE` on the left, then `Geometry DOE` on the right. Shape Preview follows DOE Case immediately, before the prevention state and editable process/geometry details, so both presets remain visibly connected to their preview and controls.

## Content voice
- Tone: concise engineering UI copy.
- Terminology: keep `Laminate`, `Injection`, `Pt`, `Sprue`, `Filling`, `Forecast`.
- Microcopy rules: avoid explaining UI mechanics inside the main app surface; workspace titles should describe the product role (`Forecast Workspace`) rather than generic app wording. Research purpose copy may appear near the top of Laminate screens when it explains why the AI model exists, not how to operate controls. Korean forecast surfaces use Korean-first labels while retaining established engineering names such as XAI and Moldex3D; specialized upload formats belong in progressive help disclosures rather than permanent instructional blocks. The established Laminate and Injection screens use `/` as the Korean-first canonical route with matching `/ko` and `/en` language paths; the redesigned screens live at `/v2`, `/v2/ko`, and `/v2/en`. Language switchers stay within the active screen generation, use self-named `한국어` and `English` labels, and restore editable forecast conditions when language changes. Static and runtime-generated copy must come from the same per-module locale pack so charts, status messages, XAI, validation help, and design-space tooltips do not fall back to the wrong language.

## Implementation constraints
- Framework/styling system: SwiftUI for iOS, native Android Kotlin Views for Android, plain HTML/CSS/JavaScript for the ImperialAX web workspace and DD Laminate web app.
- Design-token constraints: the established Laminate and Injection web screens share a small repo-native family-shell CSS/JS layer for common tokens, components, responsive rules, and header utility dialogs; module-local styles retain ownership only of engineering-specific controls and visualizations. No dependency or external design-system package is introduced. Rebuild tokens remain in their existing app-local files. Monotone review tokens remain isolated in `styles-monotone.css`, and workflow redesign review tokens/behavior remain isolated in `styles-redesign.css` and `app-redesign-preview.js`.
- Performance constraints: keep charts lightweight and static unless user-triggered; the rebuild fetches prediction first, then loads XAI and design-space context concurrently so supporting analysis never blocks the core result. The Laminate viewer loads after the primary summary, pauses rendering while offscreen, and uses compact precomputed frames or typed arrays for real CAE fields instead of transferring raw solver files to the browser.
- Compatibility constraints: SwiftPM/Xcode app hosts, Android Gradle debug APKs.
- Test/screenshot expectations: run Swift tests and Android debug builds after visual changes. For ImperialAX workspace changes, verify web/iOS/Android copy and hierarchy stay aligned; for v2 web/iOS visual work, also verify separate v2 route/screen rendering and capture at least one screenshot when practical.
